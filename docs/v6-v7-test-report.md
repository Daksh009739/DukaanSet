# V6 Invoice Studio and V7 WhatsApp delivery verification

Date: 10 October 2026. Environment: Windows, Node 24, Next 16.4, headless Edge. The brief files are preserved in `docs/briefs`. Tests and PDF samples use fictional in-memory records or isolated test databases/outboxes. The merchant's port-3000 data was not reset or sent to Meta.

## Implemented scope

Smart Invoice Studio covers saved invoice PDFs, complete customer statements and real existing payment receipts; merchant branding/logo; historical issue snapshots; current collections shown separately; India-date opening/running/closing balances; PDF preview/download/print; three locales; four formats; private document retention; customer contact editing, dates and counts; generated/shared history; and reviewed VoiceOS document requests. The renderer replaces the older raster invoice/customer-statement download path with embedded searchable fonts and a preview of the same actual PDF.

WhatsApp covers prominent actions in saved invoices, sales history and customer activity; recipient review; saved preferences and independent communication language; native actual-file sharing; truthful manual attachment fallback; the official Cloud API transport; verified WABA/phone/template configuration; PDF media upload; transactional consent/opt-out; durable request keys and source-level pending-send protection; safe failure/uncertain states; signed callbacks and masked tenant-scoped history. Direct sends always use approved utility document-header templates. No auto-send campaigns, free-form window fallback or browser automation against WhatsApp are included.

## Acceptance limits

- Live official sending requires a real authorised Meta sender, secret-store credentials, three approved language mappings and HTTPS webhook setup. None was supplied. No real WhatsApp message or media upload was sent. Template/sender lookup was tested through injected transport fixtures; Meta's live API/version acceptance remains unverified.
- Vercel staging still needs its isolated persistent Node 24 backend/volume, deployment check token and verified mail sender. The existing gateway remains fail-closed; this report does not claim a successful hosted staging deployment. Production `main` is not promoted by this implementation.
- Invoices are ordinary non-GST sales documents. GST calculations/statutory classifications/e-invoicing, partial item returns and bank-verified UPI/payment links need separate financial integrations. QR uses only an explicitly saved UPI/payee and does not verify payment.
- Thermal PDFs use fixed-height pages and the selected width. Physical printers, Android/iOS share sheets and spoken accent/noise recognition were not tested. Preview canvas has accessible controls/page labels; visual/searchable PDFs are not certified PDF/UA-tagged documents.
- Unknown submissions require trusted callbacks or operational reconciliation; there is no force-resend, background worker or automatic retry queue. PDFs expire after seven days with generation-triggered cleanup. Metadata has no automated expiry job; Meta media deletion/customer portals/public document links are not implemented.
- Schema migration cannot recover merchant branding that was never stored on an older bill. Such presentation copies are labelled legacy. Long statements fail visibly at documented limits rather than showing incomplete totals. Existing old collection rows receive per-row receipt IDs because their original grouping was never recorded.
